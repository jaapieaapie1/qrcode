## Changes, one sentence each

1. **`Scanner` wasm export** (`src/lib.rs` 219–535) — a `wasm_bindgen` struct
   wrapping `qr_video::VideoDetector`, so the camera path gets ROI tracking, the
   30-frame full-scan refresh and cross-frame de-duplication instead of a naked
   `detect_all_luma` per frame.
2. **`emit_repeated: true`** (`src/lib.rs` 269) — the page needs corners on every
   frame to hold the overlay, so repeats are emitted and the *event name*
   (`first`/`repeat`/`lost`) carries the "is this new" signal instead of the
   presence of an event.
3. **Micro QR pass kept alive** (`src/lib.rs` 223–231, 366–430) — `qr-video` is
   QR-only, so dropping straight onto it would have silently removed Micro QR
   from the camera path; a full-frame `detect_micro_luma` runs every third frame
   with its own FNV-1a tracking table and the same event vocabulary.
4. **RGBA in, luma computed in wasm** (`src/lib.rs` 290–314, 501–510;
   `www/app.js` 88–104) — `scan_frame_rgba` takes the canvas buffer as-is; see
   the measurement below.
5. **Camera constraints** (`www/app.js` 326–367) — 1920×1080 `ideal` plus
   `facingMode: environment`, then `applyConstraints({ advanced })` for
   `focusMode`/`exposureMode` `continuous`, each gated on `getCapabilities()`
   advertising it, with a swallowed rejection because it is an enhancement.
6. **Resolution and cadence** (`www/app.js` 34–39) — `MAX_EDGE` 720 → 1440 and
   the scan interval 100 ms → 66 ms (~15 fps).
7. **Overlay time-to-live** (`www/app.js` 42–45, 249–269) — boxes are held
   300 ms past their last sighting, so the slower Micro cadence and the odd ROI
   miss do not make the outline blink.
8. **Status line** (`www/app.js` 118–128) — appends `— 1440×810, 5.2 ms/scan`,
   a rolling median over the last 20 frames, so a lighting or perf problem is
   visible without a console.
9. **File-input path unchanged in kind** (`www/app.js` 393–435) — still the
   stateless `scan`, so it keeps reporting the symbol version; it just gets the
   higher `MAX_EDGE` and the same status suffix.
10. **Generate section untouched** — no edit below `app.js` 469.

## JS-vs-wasm luma: the measurement

Node 22, release wasm, 1440×810 frame (1.17 Mpx), median of 30 runs after
warm-up. Script kept out of the repo (scratchpad).

| Path | ms |
|---|---|
| JS `RGBA→luma` loop | 1.96 |
| wasm `scan_frame(luma)` — 1.17 MB copy + detect | 6.77 |
| wasm `scan_frame_rgba(rgba)` — 4.69 MB copy + convert + detect | 7.76 |

JS path total 8.74 ms; wasm path total 7.76 ms. The conversion step alone is
0.99 ms in wasm against 1.96 ms in JS — the 4× wider boundary transfer is a
`memcpy` and costs less than the pixel loop it replaces. **Adopted the RGBA
entry point**, and dropped the luma one rather than ship an unused export (the
file path does its own one-shot conversion in JS, where cost is irrelevant).

## Open questions / risks

1. **QR version is `null` on the camera path.** `qr_video::Observation` carries
   the payload, corners and identity but not the symbol geometry, so the
   streaming path cannot label `QR v7` — it shows plain `QR`. Micro keeps its
   version because that pass goes through `qr_detect` directly. The file path is
   unaffected. Fixing it properly means adding `version` (and arguably `kind`)
   to `qr-video`'s `Observation`; I did not touch `crates/`. **Flagging for
   Arch** as a small qr-video API addition, not something to work around here.
2. **Binarized-view toggle: not built.** `qr-detect` keeps `mod binarize`
   private and exports only `PerspectiveTransform` and `Point` — there is no
   public type or function that yields a thresholded image. As instructed I did
   not fake it JS-side and did not touch the crate. It needs a qr-detect export
   (something like `pub fn binarize_luma(&[u8], u32, u32) -> Vec<u8>` at the
   primary window, plus the retry radius as an argument) which the sibling
   Builder owns right now. **Follow-up item.**
3. **Micro QR does not ride the ROI fast path.** It re-binarizes the full frame
   on its cadence frames, which is the dominant per-frame cost when a micro
   symbol is around. Cheaper would be reusing the QR ROI, but that ROI tracks a
   *QR* symbol, so it would be aimed wrong. The real fix is micro support inside
   `qr-video`; noted, not attempted.
4. **Phone budget is untested.** 20.5 ms worst case on this laptop could be
   80 ms+ on a mid-range phone, i.e. above the 66 ms slot. Self-limiting rather
   than broken, and visible in the status line, but if the Owner reports a
   sluggish preview the answer is `MAX_EDGE`, not the cadence.
5. **`identity_key` domain flip** (inherited from qr-video, documented there): a
   code that decodes on some frames and not others changes identity, producing a
   spurious `lost` + `first` pair. Visible here as an occasional duplicate row in
   the decoded list for a marginal symbol. Left as-is — it is qr-video's
   documented trade-off.
6. **`live` map key is the wasm identity hash**, so the overlay inherits the same
   flip; harmless, the box just re-appears under a new key within one frame.

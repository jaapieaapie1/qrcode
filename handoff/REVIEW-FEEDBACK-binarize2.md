## The `(usable, found)` tie-break — verified, not re-litigated

Arch approved the deviation; my job was to confirm it does what it claims. It does,
on all three counts:

- **Fixes the case it was introduced for.** Primary 0 candidates, retry 1
  undecodable: `(0, 1) > (0, 0)`, so the retry's detection is returned. Under plain
  `usable` with tie-to-primary it would have been a 0-0 tie and the empty vector
  would have won — a real regression against round 2. The second element is load
  bearing.
- **Collapses to round-2 semantics without `decode`.** There `usable == len`, so
  the rule reduces to: primary non-empty -> primary; primary empty -> retry iff
  non-empty, else empty. Identical to round 2's `if !primary.is_empty()` /
  `else retry` in every branch, including the both-empty one.
- **Changes nothing else.** The ranking only runs when the primary has zero usable
  results, so the first element reduces to "did the retry decode anything". Where
  neither pass decodes it falls through to a candidate count, which is the one place
  it could in principle pick a worse grid. I swept every non-decodable
  `micro_fixture` frame with a non-empty primary — M2/M3/M4 x 4/6/8/10 px x depth
  0.800-0.995 — and compared against round 2's always-return-primary rule:
  **1121 frames checked, 0 worse, 0 better.** The claim holds empirically as well as
  by construction.

Total, deterministic, and biased to the primary. No objection.

### MINOR-6 — qr-video's suite now exercises only the double-pass path

`tests/video.rs` fixtures are synthetic grids that deliberately never decode, so
under the new trigger every `detect_full` in that suite runs both passes and returns
the primary via the tie-break. Results are unchanged and all 7 pass — Bob flagged
this himself, correctly — but the consequence is that qr-video no longer covers the
*single-pass hit* path for `detect_full` at all. Not a correctness problem and not
worth blocking on; worth one decodable fixture in that suite whenever someone is
next in there, so the common case is covered by something.

## Rulings on the open questions

**1. The `(usable, found)` tie-break — keep it.** Verified above. The literal ruling
would discard a retry-only undecodable detection, which is a regression against
round 2. Arch has approved it; I concur on the evidence.

**2. The no-`decode` build keeps the weaker guarantee — correct as built.** There is
no decode outcome in that build to key on, the limitation is stated plainly in the
crate docs rather than buried, `*_single_pass` already exposes exactly what such a
caller needs to drive the second radius itself, and the behaviour is pinned by a
test that actually runs in the only config that can run it. Nothing further needed.

**3. Detected-but-not-decoded now costs 1.58x — accepted, and correctly flagged.**
This is inherent to a decode-aware trigger: those are precisely the frames a retry
can rescue, so paying for the second pass there is the feature working, not a
side effect. The blast radius is bounded — full scans are cadence-limited and the
ROI path is single-pass, so the per-frame hot path is untouched. Bob is right that
the lever, if it is ever wanted, is qr-video's full-scan interval and not this
trigger. Flagged in the open, which is the correct handling.

**4. Multi-code limitation — accept as documented,** unchanged from my round-2
ruling. Both passes on every frame to serve a case no fixture exercises is the wrong
side of the cost curve, and the crate doc paragraph is honest about what it does not
cover.
